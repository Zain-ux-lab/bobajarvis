# How I built this with AI

I used AI tools throughout, as a pair programmer that writes code quickly, while I own the product, the decisions and the verification. Most of the code was generated by Claude Code from my specification and feedback. Every change is a separate commit with its reason, so the history shows how the project moved.

## My part

- **Problem and user.** I chose the lone bubble tea barista: hands on the shaker, eyes on the cup, so the product had to be voice-only through an earpiece (Productivity track).
- **The specification.** I wrote the requirements and the rules the code must follow: the LLM never changes state; completing an order needs the barista's exact words as evidence; no silent keyword fallback when the LLM is unavailable; simulated shop data is labelled as simulated; no API keys in the browser, logs or git; no paid services.
- **Decisions.** Local Whisper for transcription. Connecting a real POS through Square's sandbox (import open orders, mark an order ready). Cutting latency and adding audio cues after testing it. Choosing Groq with a backup chain once the benchmark showed Gemini's free tier was the bottleneck. After feedback from engineers in an office-hours session, scoping down: polish what exists, measure speed, and explain the choices, rather than adding features.
- **Testing as the user.** I ran voice sessions with a real microphone and found the problems the unit tests could not: "drink" heard as "ring", a general stock question answered with a question, "How much oat milk?" reading out every milk, "What comes after sugar?" skipping a step, units read as the letter "L", and slow turns while recording. Each one was fixed and, where possible, added to the tests or the benchmark (`VALIDATION.md` lists them).
- **Demo.** I wrote, recorded and edited the demo video.

## How I kept control of AI-written code

- **Nothing the model says is trusted at runtime.** Its output is constrained by a JSON schema, validated with Zod, and re-checked by the executor against real state.
- **Tests and measurement, not impressions.** 54 unit tests for the executor, validation and provider handling; a 27-phrase live benchmark (`npm run bench`) that checks the chosen action, and the step number for recipe questions; 27/27 on the final run.
- **Small, reviewable changes.** One commit per change, each with what was wrong and how it was checked.
- **Honest records.** `VALIDATION.md` states what was tested, what was not, and every bug found along the way.

## Design decisions

1. **The LLM picks actions; code changes state.** `/api/jarvis` returns a plan of up to 4 actions from 12 types. `executePlan()` in `src/lib/executor.ts` is the only place shop state changes and does all arithmetic, so the model cannot invent quantities or tickets.
2. **Three validation layers.** The provider's JSON schema shapes the output, Zod (`normalizePlan`) validates it, and the executor checks it against real state (does the order exist, is the unit compatible).
3. **Completion needs evidence.** Completing an order is the only irreversible action, so `completionEvidence` must be a quote found in the transcript. A misheard "got it" can never complete an order.
4. **Atomic and idempotent.** The executor works on a `structuredClone`; any failing action rolls back the whole plan. The `deducted` flag means ingredients come off exactly once.
5. **One ingredient function.** `drinkLines()` produces both the spoken steps and the stock deductions, so they cannot disagree.
6. **Latency by measurement.** Local `whisper-server` (~0.2 s); 650 ms of silence ends a sentence; a smaller prompt; Groq first with reasoning set low; then `callWithBackup` switches to Groq 120b and Gemini on rate limits or outages but never on auth errors. Median 0.69 s for the LLM step on the final run.
7. **A voice loop that can't hear itself.** In `src/lib/earpiece.ts` the mic is ignored unless the state is Listening, and a `generation` counter drops any result from a turn that was interrupted.
